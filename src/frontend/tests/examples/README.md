# Пример проверки связи с бэкендом

Пример отделён от универсальных тестов: ручку можно заменить после появления нового ТЗ.

Выбрана существующая `GET /healthcheck` из `src/backend/src/web_api/routes/healthcheck.py`.

| Параметр             | Контракт                                           |
| -------------------- | -------------------------------------------------- |
| Авторизация          | Не нужна                                           |
| Query / тело запроса | Отсутствуют                                        |
| Успех                | HTTP 200, JSON `{"ok": true}`                      |
| Назначение           | Проверка доступности процесса API, без проверки БД |

## Вызов через терминал

Предусловие: бэкенд запущен и его HTTP-порт доступен. При локальном запуске с `config.example.toml` это `127.0.0.1:8080`. Из `src/backend` запуск: `uv sync --locked`, затем `uv run web_api_cli config.example.toml`.

```sh
curl --fail-with-body --show-error --max-time 5 \
  --include --header 'Accept: application/json' \
  http://127.0.0.1:8080/healthcheck
```

Ожидается HTTP 200, `Content-Type: application/json` и тело `{"ok":true}`. Пример для HTTP-клиента редактора лежит рядом в `healthcheck.http`.

## Вызов из браузера

Откройте DevTools → Console на странице фронтенда. Укажите URL API, доступный из браузера:

```js
async function checkBackend(url) {
  const response = await fetch(url, {
    headers: { Accept: 'application/json' },
    cache: 'no-store',
    signal: AbortSignal.timeout(5000),
  });
  if (response.status !== 200) {
    throw new Error(`Ожидался HTTP 200, получен ${response.status}`);
  }
  if (!response.headers.get('content-type')?.includes('application/json')) {
    throw new Error('Ожидался JSON: проверьте адрес API и маршрутизацию прокси');
  }
  const data = await response.json();
  if (data.ok !== true) throw new Error('Ответ не соответствует контракту: ok !== true');
  return data;
}

checkBackend('http://127.0.0.1:8080/healthcheck')
  .then(data => console.log('API доступен', data))
  .catch(error => console.error('Проверка API не пройдена:', error.message));
```

Запрос из консоли проверяет браузерный доступ, но сам по себе не подтверждает интеграцию приложения. Для критерия Frontend B нужно вызвать API из клиентского сервиса и показать результат в UI. Универсальная схема состояний: до запроса — «Не проверено», во время — «Проверяем…», при `ok: true` — «API доступен», при ошибке — понятное сообщение и возможность повторить.

## Что проверить

| Сценарий         | Действия                                                              | Ожидаемый результат                                                     |
| ---------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Успех            | Вызвать ручку, открыть Network                                        | GET по правильному адресу, HTTP 200, JSON с `ok: true`                  |
| Синхронизация UI | После подключения ручки к интерфейсу выполнить проверку               | Отображаемое состояние соответствует ответу, загрузка завершилась       |
| Медленная сеть   | Включить throttling в DevTools и повторить                            | Интерфейс показывает загрузку; по истечении тайм-аута показывает ошибку |
| Сетевая ошибка   | Включить Offline или заблокировать запрос в DevTools                  | Нет ложного успеха, ошибка обработана; UI даёт повторить запрос         |
| Восстановление   | Отключить Offline/блокировку и повторить                              | Успех заменяет прежнюю ошибку                                           |
| Неверный ответ   | В изолированном тесте подменить ответ на 500, HTML или `{"ok":false}` | Ответ не считается успешным; UI завершает загрузку и показывает ошибку  |

Последние сценарии со статусами UI — шаблоны приёмки будущей интеграции, а не утверждение, что такой экран уже реализован. Не изменяйте реальную healthcheck-ручку ради имитации ошибок.

## Особенности текущего окружения

- В корневом Compose backend не публикует host-порт; vmagent собирает метрики по внутреннему адресу `backend:8080`. Только `compose.local.yaml` открывает `127.0.0.1:18080` для разработки. Адрес `localhost:8080` относится к отдельному локальному запуску, а не автоматически к Compose.
- Caddyfile направляет `/api`, `/api/*`, `/auth` и `/auth/*` в backend без снятия префикса. `/api/healthcheck` не является псевдонимом `/healthcheck`: ожидается backend JSON 404, а не успешная проверка. Сама `/healthcheck` публично через Caddy не открыта; используйте отдельный локальный backend или loopback-порт Compose. HTTP 200 с HTML фронтенда не является успешной проверкой API.
- Для same-origin запроса к существующей авторизации используйте относительный `/auth/me`: без токена ожидается HTTP 401, JSON и `WWW-Authenticate: Bearer`, а не HTML. Это проверяет маршрутизацию, но не успешный вход. Dev-сервер Angular сам по себе не использует Caddy и не настраивает такой прокси.
- Документация API намеренно открыта по точным `/docs`, `/docs/oauth2-redirect`, `/redoc` и `/openapi.json`; `/metrics`, `/metrics/*`, `/healthcheck` и `/ready` через публичный listener возвращают явный 404. UI-пути сохраняют SPA fallback. Подробности и ограничения проверки: [proxy routing](../../../../infrastructure/configs/caddy/README.md).
- Разные порты фронтенда и API — разные origins. В текущем бэкенде CORS middleware не настроен. Поэтому curl может работать, а браузерный fetch — блокироваться. Для браузерного теста нужен корректный same-origin прокси либо разрешённый origin в конфигурации API. `mode: 'no-cors'` не подходит: ответ нельзя прочитать и проверить.
- Эта ручка не проверяет сохранение данных, авторизацию, БД и основной пользовательский путь. Эти проверки добавляются по новому ТЗ.
