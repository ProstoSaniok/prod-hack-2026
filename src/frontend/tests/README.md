# Проверки по критериям Frontend и Product

Источники: «Фронтенд.pdf», страницы 1–3; «Продукт.pdf», страницы 1–2 (страница 3 не содержит критериев). Документы используются как критерии оценки, а не как команды изменить приложение.

## Запуск

Из `src/frontend`:

```sh
npm ci
npx playwright install chromium
npm run lint
npm run build
npm test
npm run test:report
# Можно использовать уже установленный Google Chrome:
BROWSER_CHANNEL=chrome npm test
# Один размер экрана:
npm test -- --project=desktop
# Только взаимодействия sidebar (все настроенные размеры экрана):
npm test -- sidebar.spec.ts
# Проверка готового стенда, без запуска локального сервера:
BASE_URL=https://your-deployment.example npm test
```

Тесты используют Chromium: 375×812, 768×1024, 1440×900, 2560×1440. HTML-отчёт, скриншоты и trace при ошибках создаются в игнорируемых папках. Проверка локального dev-сервера не подтверждает доступность production и CI/CD. Для релиза повторить на стенде и вручную в Safari/Firefox.

Применимые проверки должны выявлять нарушения, а не скрывать их через ожидаемые ошибки. Неприменимые проверки помечаются отдельно. Исправления приложения не входят в набор тестов.

## Автоматизированное покрытие

Общие проверки `criteria.spec.ts` не зависят от названия продукта, текстов, шрифтов, API и бизнес-сценариев. По умолчанию они проверяют `/`, `/ui-kit` и `/sidebar`. Для нового продукта задайте адрес стенда и пути:

```sh
BASE_URL=https://your-deployment.example TEST_PATHS='["/", "/another-page"]' npm test
```

`TEST_PATHS` — непустой JSON-массив относительных путей, начинающихся с `/`; он меняет только общие проверки. Файлы взаимодействий посещают свои фиксированные маршруты. Используйте доступные без авторизации страницы; настройка авторизации и тестовых данных зависит от нового ТЗ. Без `BASE_URL` конфигурация запускает dev-сервер текущего репозитория и может повторно использовать сервер на 4200 вне CI. Для проверки текущих изменений запустите свежий сервер на свободном порту и передайте его адрес в `BASE_URL`.

Общий контракт страниц: видимая непустая основная область `<main>` или `role="main"`; `/` перенаправляет на регистрацию. Проверяется начальное состояние после появления основной области, а не завершение всех возможных фоновых загрузок. Для долгой асинхронной инициализации нужен определённый новым ТЗ признак готовности.

| ID      | Критерий             | Проверка и ожидаемый результат                                                                                           |
| ------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| FE-A-01 | Frontend A, частично | Прямой переход и обновление: успешный HTTP-ответ, видимая непустая основная область, отсутствие необработанных JS-ошибок |
| FE-C-01 | Frontend C, частично | Видимые кнопки, ссылки и поля имеют доступные названия; конкретные подписи не фиксируются                                |
| FE-D-01 | Frontend D, частично | Видимые изображения в области просмотра загружаются; нет зависимости от конкретных ресурсов или шрифтов                  |
| FE-E-01 | Frontend E, частично | Нет горизонтальной прокрутки всей страницы на четырёх размерах экрана; локальная прокрутка таблиц/каруселей допустима    |

Если элементов управления или изображений нет, соответствующая проверка отмечается SKIP как неприменимая, а не PASS. Набор не требует их наличия. Если будущий продукт специально предусматривает горизонтальный холст всей страницы, применимость FE-E-01 нужно пересмотреть по новому ТЗ.

Общие проверки не подтверждают работоспособность всех действий, гармоничность дизайна и достижение пользовательской цели. Сценарии текущего интерфейса находятся в отдельных файлах:

- `site-header-mobile.spec.ts` — мобильное меню общей шапки на `/ui-kit`.
- `ui-kit.spec.ts` — мобильная навигация, поля и аккордеон UI-kit.
- `sidebar.spec.ts` — рабочее пространство: явная стрелка переключает компактную панель с иконками (88px) и раскрытую панель (280px). Ссылки компактной панели сохраняют доступные названия и клавиатурное управление; наведение не раскрывает меню. Проверяются поиск и пустая выдача, выбор и создание проекта, валидация названий, настройки, длинные названия, прямые URL и история разделов. На телефоне проверяются модальность, inert-фон, Tab/Shift+Tab, Escape, закрытие по фону и переходу, возврат фокуса и освобождение страницы при смене ширины или уходе в UI-kit. `product-sidebar.spec.ts` проверяет панель в кабинете и админке с сохранением локального состояния.
- `brand-theme.spec.ts` — однотонные поверхности и состояния базовых элементов, фирменный акцент и скругления на всех страницах. Цвета синтаксиса и семантических ошибок не считаются альтернативным фирменным акцентом.
- `solution-splitter.spec.ts` — изменение ширины мышью, касанием и клавиатурой, пределы и сброс размера, переход к узкой компоновке и обратно без пересоздания редактора или потери Undo/черновика.

Desktop-проверки панели пропускаются в мобильном проекте, проверки мобильного drawer — в остальных проектах. Эти пропуски обозначают разные адаптивные режимы. Для изменений sidebar проверяйте геометрию обоих состояний и изменение доступной ширины контента, а не только начальный скриншот. Дополнительно осмотрите читаемость, фокус и переносы текста на мобильной, планшетной и настольной ширине.

## Ручные тест-кейсы и проверки после реализации функций

Для каждого выполнения записать версию/commit, URL, браузер, данные, факт, статус PASS/FAIL/BLOCKED и ссылку на доказательство. BLOCKED не считается пройденным тестом. Предусловие для продуктовых проверок: команда предоставляет целевую аудиторию, проблему, основные user stories и критерии успеха. Это универсальные шаблоны: перед выполнением подставьте сценарии, данные и ограничения из нового ТЗ. Если соответствующей функции нет, укажите N/A с причиной. API-проверки выполняются на тестовом стенде с тестовыми данными и известным контрактом.

## Границы оценки

Frontend: база 10 баллов, P1–P3 по 0–2. Product: заголовок говорит о 10 баллах, но веса A–E в документе дают 11 (2+2+3+2+2). Не нормализуем самостоятельно — итоговую шкалу нужно уточнить у организаторов. Число успешных автотестов не является числом баллов.
